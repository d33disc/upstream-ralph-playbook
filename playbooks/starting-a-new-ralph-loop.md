# Playbook: Starting a New Ralph Loop

A step-by-step guide for beginners on how to set up and start a new Ralph loop from scratch.

---

## What Is a Ralph Loop?

A Ralph loop is an autonomous AI coding workflow where a bash script continuously feeds a prompt to an LLM (e.g., Claude), which then reads specs, selects a task, implements it, runs tests, commits, and exits — at which point the loop restarts with a fresh context window to pick up the next task. The result is iterative, automated software development driven by specifications you define.

---

## Prerequisites

Before starting, make sure you have the following installed and available:

### Required Tools

| Tool | Purpose | Install |
| --- | --- | --- |
| **Git** | Version control for your project | [git-scm.com](https://git-scm.com/) |
| **Claude CLI** | Anthropic's command-line interface for Claude | `npm install -g @anthropic-ai/claude-cli` or see [Anthropic docs](https://docs.anthropic.com/en/docs/claude-cli) |
| **Node.js** (optional) | Required only if using `loop_streamed.sh` with `parse_stream.js` | [nodejs.org](https://nodejs.org/) |
| **Code editor** | For editing specs and prompt files (VS Code, Vim, etc.) | Your preference |

### Required Knowledge

- **Basic command-line usage** — navigating directories, running scripts, using Git.
- **Basic Git knowledge** — committing, pushing, branching.
- **Familiarity with Markdown** — specs, prompts, and plans are all Markdown files.
- **Understanding of your project's language/framework** — Ralph builds _your_ project; you need to understand what it's building.

### Recommended

- **A sandbox environment** — Ralph runs with `--dangerously-skip-permissions`, which bypasses all permission prompts. Run in an isolated environment (Docker, [Fly Sprites, E2B, or exe.dev](../references/sandbox-environments.md)) to limit blast radius.
- **An Anthropic API key** — required for the Claude CLI.

## Step 1: Create Your Project Repository

Start with a Git repository for your project.

```bash
mkdir my-project
cd my-project
git init
```

If you already have a repository, clone it and navigate into it:

```bash
git clone https://github.com/your-org/your-project.git
cd your-project
```

---

## Step 2: Set Up the Project Structure

Ralph expects a specific file layout. Create the following structure in your project root:

```
project-root/
├── loop.sh                         # Ralph loop script
├── PROMPT_build.md                 # Build mode instructions
├── PROMPT_plan.md                  # Plan mode instructions
├── AGENTS.md                       # Operational guide loaded each iteration
├── IMPLEMENTATION_PLAN.md          # Prioritized task list (generated by Ralph)
├── specs/                          # Requirement specs (one per topic)
│   ├── 01-topic-a.md
│   └── 02-topic-b.md
└── src/                            # Your application source code
    └── lib/                        # Shared utilities & components
```

Create the directories and placeholder files:

```bash
mkdir -p specs src/lib
touch AGENTS.md IMPLEMENTATION_PLAN.md
```

---

## Step 3: Copy the Loop Script

Copy the `loop.sh` script into your project root. You can use the version from this playbook repository:

```bash
cp /path/to/ralph-playbook/files/loop.sh ./loop.sh
chmod +x loop.sh
```

Or create it manually — the minimal form is:

```bash
#!/bin/bash
while :; do cat PROMPT_build.md | claude -p --dangerously-skip-permissions --model opus --verbose; done
```

The enhanced version in this repository's [`files/loop.sh`](../files/loop.sh) adds mode selection (plan/build), max-iteration limits, and automatic `git push` after each iteration.

> **Tip:** If you want color-coded streaming output, also copy [`loop_streamed.sh`](../files/loop_streamed.sh) and [`parse_stream.js`](../files/parse_stream.js).

## Step 4: Create the Prompt Files

You need two prompt files — one for **planning** and one for **building**.

### `PROMPT_plan.md`

This prompt tells Ralph to analyze your specs vs. your code and generate/update an implementation plan — without implementing anything.

```markdown
0a. Study `specs/*` with up to 250 parallel Sonnet subagents to learn the application specifications.
0b. Study @IMPLEMENTATION_PLAN.md (if present) to understand the plan so far.
0c. Study `src/lib/*` with up to 250 parallel Sonnet subagents to understand shared utilities & components.
0d. For reference, the application source code is in `src/*`.

1. Study @IMPLEMENTATION_PLAN.md (if present; it may be incorrect) and use up to 500 Sonnet subagents to study existing source code in `src/*` and compare it against `specs/*`. Use an Opus subagent to analyze findings, prioritize tasks, and create/update @IMPLEMENTATION_PLAN.md as a bullet point list sorted in priority of items yet to be implemented. Ultrathink. Consider searching for TODO, minimal implementations, placeholders, skipped/flaky tests, and inconsistent patterns. Study @IMPLEMENTATION_PLAN.md to determine starting point for research and keep it up to date with items considered complete/incomplete using subagents.

IMPORTANT: Plan only. Do NOT implement anything. Do NOT assume functionality is missing; confirm with code search first. Treat `src/lib` as the project's standard library for shared utilities and components. Prefer consolidated, idiomatic implementations there over ad-hoc copies.

ULTIMATE GOAL: We want to achieve [YOUR PROJECT-SPECIFIC GOAL HERE]. Consider missing elements and plan accordingly. If an element is missing, search first to confirm it doesn't exist, then if needed author the specification at specs/FILENAME.md. If you create a new element then document the plan to implement it in @IMPLEMENTATION_PLAN.md using a subagent.
```

> **Important:** Replace `[YOUR PROJECT-SPECIFIC GOAL HERE]` with your actual project goal.

### `PROMPT_build.md`

This prompt tells Ralph to pick a task from the plan, implement it, run tests, commit, and push.

Copy the template from [`files/PROMPT_build.md`](../files/PROMPT_build.md) or use the template documented in the main [README](../README.md#prompt_buildmd-template).

---

## Step 5: Set Up `AGENTS.md`

`AGENTS.md` is loaded every iteration and tells Ralph how to build, test, and run your project. Start with a minimal template:

```markdown
## Build & Run

[How to build and run your project — e.g., `npm install && npm run dev`]

## Validation

Run these after implementing to get immediate feedback:

- Tests: `[your test command, e.g., npm test]`
- Typecheck: `[your typecheck command, e.g., npx tsc --noEmit]`
- Lint: `[your lint command, e.g., npm run lint]`

## Operational Notes

[Leave empty initially — Ralph will populate this with learnings]

### Codebase Patterns

[Leave empty initially — Ralph will populate this with discovered patterns]
```

> **Tip:** Start with minimal content. Ralph will update `AGENTS.md` with operational learnings as it works. Over-specifying upfront can degrade results.

## Step 6: Define Your Requirements as Specs

This is the most important step. Specs define _what_ Ralph should build.

### How to Write Specs

1. **Identify Jobs to Be Done (JTBD)** — What does your user need to accomplish?
2. **Break each JTBD into Topics of Concern** — Each topic gets its own spec file.
3. **Apply the "One Sentence Without 'And'" test** — If you need "and" to describe a topic, it's probably multiple topics.

### Spec File Naming

Use the format `specs/NN-kebab-case.md`:

```
specs/01-user-authentication.md
specs/02-image-upload.md
specs/03-color-extraction.md
```

### Spec Content Guidelines

Each spec should include:

- **Topic statement** — One sentence describing what this topic covers.
- **Scope** — What's in-scope and what's a boundary.
- **Data contracts** — Inputs and outputs.
- **Behaviors** — Observable outcomes (not implementation details).
- **State transitions** — How state changes.

### What NOT to Put in Specs

- ✗ Code blocks or implementation details
- ✗ Variable names, function names, or file paths
- ✗ Library or framework references
- ✗ HOW to implement — only WHAT the outcome should be

> **Example of a good acceptance criterion:**
> ✓ "Extracts 5-10 dominant colors from any uploaded image"
>
> **Example of a bad acceptance criterion:**
> ✗ "Use K-means clustering with 3 iterations on pixel RGB values"

## Step 7: Run Your First Loop (Planning Mode)

Before building anything, generate an implementation plan:

```bash
./loop.sh plan
```

This will:

1. Feed `PROMPT_plan.md` to Claude.
2. Claude studies your specs and any existing code.
3. Claude generates/updates `IMPLEMENTATION_PLAN.md` with prioritized tasks.
4. Changes are pushed to your Git remote.
5. The loop restarts for another pass (planning often completes in 1-2 iterations).

Stop the loop with **Ctrl+C** once the plan looks good.

### Review the Plan

Open `IMPLEMENTATION_PLAN.md` and verify:

- Tasks are prioritized correctly.
- Nothing critical is missing.
- Tasks are appropriately scoped (not too broad, not too narrow).

If the plan needs adjustment, edit your specs and rerun `./loop.sh plan`.

---

## Step 8: Run the Build Loop

Once your plan is ready, start building:

```bash
./loop.sh build
```

Or limit to a specific number of tasks:

```bash
./loop.sh build 10    # Stop after 10 tasks
./loop.sh 20          # Shorthand: build mode, 20 tasks
```

Each iteration will:

1. Study specs and the current plan.
2. Pick the most important remaining task.
3. Investigate existing code (to avoid reimplementing what exists).
4. Implement the task.
5. Run tests against backpressure (build, lint, typecheck).
6. Update `IMPLEMENTATION_PLAN.md` (mark task done, note discoveries).
7. Commit and push.
8. Exit — loop restarts with fresh context.

---

## Step 9: Monitor and Course-Correct

### Watch the First Few Loops

Especially early on, observe Ralph's behavior:

- Is it picking the right tasks?
- Is it following your project's patterns?
- Are tests passing?
- Is the implementation quality acceptable?

### Course-Correct When Needed

| Problem | Solution |
| --- | --- |
| Ralph generates wrong patterns | Add utility code or examples in `src/lib/` for Ralph to discover and follow |
| Ralph ignores instructions | Add guardrails to `PROMPT_build.md` (use the `999...` numbering for priority) |
| Plan is stale or wrong | Stop the loop, delete `IMPLEMENTATION_PLAN.md`, run `./loop.sh plan` to regenerate |
| Ralph goes in circles | Stop the loop, review plan, adjust specs, regenerate plan |
| Tests aren't catching issues | Add more backpressure — more tests, stricter lint rules, type checking |

### Escape Hatches

- **Ctrl+C** — Stops the loop immediately.
- **`git reset --hard`** — Reverts uncommitted changes.
- **Delete and regenerate the plan** — Switch to `./loop.sh plan` to create a fresh plan.

---

## Step 10: Document and Iterate

As your project takes shape:

1. **Review `AGENTS.md`** — Ralph updates this with operational learnings. Review it periodically to ensure it stays concise and accurate.
2. **Review `IMPLEMENTATION_PLAN.md`** — Verify completed tasks are marked done and new discoveries are captured.
3. **Update specs as needed** — If requirements change, update the relevant spec files and regenerate the plan.
4. **Add dependencies and setup docs** — Document any dependencies your project has in a `README.md` or similar.

Use this checklist to verify your setup before running your first loop:

- [ ] Git repository initialized
- [ ] Claude CLI installed and authenticated
- [ ] `loop.sh` copied and made executable (`chmod +x loop.sh`)
- [ ] `PROMPT_plan.md` created with your project goal
- [ ] `PROMPT_build.md` created
- [ ] `AGENTS.md` created with build/test/lint commands
- [ ] `IMPLEMENTATION_PLAN.md` created (can be empty — Ralph generates content)
- [ ] `specs/` directory created with at least one spec file
- [ ] `src/` directory created for your source code
- [ ] Running in a sandbox or isolated environment
- [ ] On a dedicated Git branch for Ralph's work

## Common Beginner Mistakes

| Mistake | Why It's a Problem | Fix |
| --- | --- | --- |
| Over-specifying `AGENTS.md` | Verbose inputs degrade determinism | Start minimal; let Ralph fill in learnings |
| Putting implementation details in specs | Constrains Ralph's ability to make good decisions | Specify WHAT (outcomes), not HOW (approach) |
| Not running in a sandbox | `--dangerously-skip-permissions` bypasses all safety checks | Always use a sandboxed environment |
| Skipping planning mode | Ralph builds without direction, wastes iterations | Always run `./loop.sh plan` first |
| Specs that are too broad | "The user system handles auth, profiles, and billing" = 3 topics | Apply the "One Sentence Without 'And'" test |
| Not watching early loops | Miss patterns that need correction | Observe the first 3-5 iterations closely |
